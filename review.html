Flagged for review and repository audit

Unverified figures, modelling caveats and the repository audit.

What this page is for

Three lists. The first is every figure on this site that is not verified against an official source, and where the record for it is actually held. The second is every modelling shortcut that materially affects the answer. The third is the audit of the repository this site is built from. None of these block the recommendation, but each one is a reason to check before acting.

How the model works

Method, in one paragraph

A deterministic model, rebuilt from assets/data/inputs.json and assets/data/series.json by scripts/model.py. House prices grow at a stated nominal rate, the assessed value rolls forward under the published rules with an inflation cap, fixed charges grow with inflation, running costs are inflated at the same rate, and each path is valued at the end of a thirty year horizon after selling costs and tax. On the paths that keep or let the house, every year's property tax and running costs are deducted at their compounded future value at the after-tax equity return, so the living and letting paths bear the same cash costs that the sell paths are spared. Every monetary result is rounded to the nearest $10 before it is printed. There is no randomness, so the same inputs always produce the same outputs.

Line-by-line audit of the two roll tables

What was checked, and what could not be

The two tables on the Property A and Property B pages are the owner's own records. This audit re-derives every number in them with arithmetic only. It does not compare them with the county's roll, because that record is held by the county, whose name and pages are deliberately withheld from this public site; ordering the assessor's parcel history is a task for the owner, and it is the first item on the list below.

R-1. Every published year-over-year percentage reproduces exactly

Each row's assessed value and bill were divided by the row above it. The resulting percentages match the owner's published changes in all 11 Property A pairs and all 9 Property B pairs. No transcription error was found in either table.

R-2. The assessed value never exceeds the Proposition 13 cap

No year in either table grows faster than 2%. Property A grew 2.0% in ten of eleven pairs and 1.0% and 1.5% in two others; Property B grew 2.0% in eight of nine. This is what a long-held base-year value looks like, and it is consistent with the Proposition 13 cap having bound in every year shown. Property A's assessment of $539,740 on a house valued near $3,100,000 is the single largest number in the analysis: it is the shelter.

R-3. The 2% cap does not bound the whole bill, and on Property B it bounds barely half of it

Only the ad valorem part of a property tax bill is limited by the cap. The rest - fixed charges, special assessments and district levies - is set separately. Splitting each bill at the stated ad valorem rate shows the fixed part is 11.7% of Property A's bill and 44.7% of Property B's. The arithmetic ceiling follows: the cap can bound at most 88.3% of Property A's bill and 55.3% of Property B's.

This matters most on the property the heir already owns. Property B's fixed charges rose from $540 in 2016 to $1,090 in 2025, which is 8.12% a year over that window - and the jump happened in one year, 2018, when the fixed part rose by $290. The bill in that year rose 18.4% on an assessed value that rose 2.0%.

R-4. Reporting the growth in two windows gives two different answers, and both are true

The recent window is calm: over 2020-2025 the fixed part grew 2.36% a year on Property B and 2.29% on Property A. The long window is not: 8.12% a year on Property B and 0.79% on Property A. One of these is a level and one is a step, and the site publishes both so neither can be presented alone. A single growth rate chosen from the recent window would quietly assume the step never repeats.

R-5. The model's fixed-charge assumption sits between the two properties, not above both

The model grows the fixed part at 2.5% a year, slightly above Property A's eleven-year average of 0.79% and well below Property B's nine-year average of 8.12%. It is stated in the inputs file as deliberately conservative. The effect is that every projected bill on this site is more likely to be too low than too high, and Property B's bills are the ones most exposed, because it carries the larger fixed share. Not corrected in the model in this pass, because changing an assumption moves every published figure and the owner should choose the rate; the exposure is published instead.

R-6. The ad valorem rate cannot be identified from these bills, and the site must not pretend otherwise

The stated rate for Property A is 1.18%. With it, the fixed part of the bill works out between $750 and $1,030 across thirteen years: it does not trend, so the rate is consistent with the bills. But that is a test the rate passes, not a test that identifies it. Assessed value grows at 2% and so does the bill, so a higher rate paired with a lower fixed part fits almost as well. The honest statement, which the inputs file now carries, is that the rate is a published-law figure and the fixed part is the residual.

R-7. The audit is of arithmetic, not of the county's record

Six findings above can be established from the tables alone. None of them confirms that the tables match the assessor's roll, that the bills were paid, or that either property's tax rate area is the one assumed. Those need the county record and are listed as open questions on the questions page.

Every assumption now carries a band, and the band says what it is

The first edition of this analysis used round point values: 4% house growth, 7% equities, 5.5% selling costs. A single point value is read as a forecast even when it is labelled an assumption, and a decision that only works at one value is not a decision. Every assumption the model uses is listed below with a low and a high case. 3 of them rest on a measurement or a published figure; the rest are stated scenarios.

The distinction is the point of the table. A measured band can be checked against the source in the last column. A stated scenario cannot, and no amount of arithmetic will make it so - the honest treatment is to publish it as judgement and show how much the answer moves when it is wrong, which the what-if page and the black-swan page do.

Does the one-page brief actually fit on one page?

A measurement, and what it is not

The brief is published as a one-page sheet, and the page title, the menu and the print toolbar all say so. That claim had never been checked, because no browser is available in the build environment. This session measured it instead.

The brief's printed height is estimated at 94% of one letter-size sheet (696pt against 737pt of usable page height), across 7 sections set in 4 rows of a two-column grid at 7.1pt with 0.38in margins. It is estimated to fit on one letter-size page.

How the measurement works, and why it is an estimate. The geometry is read out of assets/style.css rather than repeated here, so changing the print rules changes the estimate and the two cannot drift apart. The estimate assumes a pessimistic average character width, does not allow for margins between blocks collapsing, and adds a safety margin to the total, so it runs long rather than short. It is still a model of a browser, not a browser.

What changed because of it. The brief as published before this check was estimated at 129% of a sheet (954pt against 737pt): it would have run onto a second page while claiming to be one page. It is now at 94%. Four changes brought it inside the sheet, and none of them removed a figure, a question or a caveat. The seven sections were re-ordered so that the two longest sit side by side in the two-column grid instead of beside short ones, which is what a two-column layout is for, and so that the sheet reads in the order an adviser would want: the decision, the questions to ask, the options and their risks, what is not known, the mixed paths, the timing, the glossary. The print type was set from 7.4pt to 7.1pt with tighter spacing. The screen lede was removed from the printed sheet, because the title already says what the document is. And the section text was shortened.

What is still open. Nobody has seen the printed sheet. Open briefing.html in a browser, print it, and check that it is one page and that the type is legible at 7.1pt. The build now fails if the estimate ever exceeds a sheet again, so an edit that breaks the promise is caught before it is published.

Privacy audit of this repository's own history

What the history audit found, and what it did not do

The published site is scanned on every build for names, street addresses, postal codes, parcel numbers, telephone numbers, email addresses, property-level place names and the county and city names, and for any dollar figure that is not a multiple of ten. That scan covers the deployable artifact, not the Git history behind it.

A separate read-only audit therefore walks every commit reachable in this repository and counts how many file versions carry the shape of each identifier. It reports counts only. It does not print a matching value, because publishing the value in order to disclose it would recreate exactly the exposure being disclosed.

The result is that the current published tree is clean on every class, and the history is not clean on three of them. No street address, parcel number or telephone number has ever been committed. Postal codes, property-level place names and the two jurisdiction names did appear in superseded file versions and in archive material, none of which is part of the published artifact. The full counts are below.

Cleaning the history is a different operation from cleaning the site: it needs a rewrite and a force-push of a public branch, which invalidates every clone, every open pull request and every fork, and cannot recall copies already downloaded. That is the owner's decision, it is recorded as an open item, and the procedure and its costs are written up for the owner. Until that decision is taken, this page states the exposure rather than claiming it has been removed.

How the history audit works

  • scripts/privacy_scrub_audit.py runs git log --all and git log --name-only, reads every distinct file version, and tests it against the same identifier patterns the live publication gate uses. It writes nothing and changes nothing.
  • The amount class is evaluated the way the live gate evaluates it: the formatted amount is parsed and its value tested, so a rounded figure is never counted and a pre-rounding figure always is. Official statutory amounts are exempted exactly as the gate exempts them.
  • The audit knows its own limits. It cannot see pull-request diffs, forks, or copies outside this repository, and it cannot certify that a deleted object is unreachable on the hosting service.
